## 1. 한 줄 목표

socratic-learn-2 에 RAG/벡터DB 도입 여부를 판단한다. 우선 use case 는 "답변 평가
근거 강화"(기존 개념 설명본을 Firestore 내장 벡터 검색으로 찾아 평가 프롬프트에
주입), 인프라는 Firestore 내장으로 한정, 익명화 후 교차 재사용 허용, 판단 기준은
체감 품질 개선 / 비용 대비 효과 / 구현·운영 복잡도다.

## 3. 기술적 가능성 (사실 근거)

도입 자체는 기술적으로 가능하다. 두 조각으로 나뉜다.

### 3.1 벡터 저장·검색 -> 추가 벤더 없이 가능

- `functions/package.json` 에 `firebase-admin ^13.10.0` 이 이미 있다. `functions/src/sessions.ts:2`
  가 `getFirestore` 로 Firestore 를 쓴다(세션 영속화 경로 `sessions/{uid}/items/{sessionId}`).
- Firestore 는 KNN 벡터 검색(`findNearest`)을 **GA(정식)** 로 지원한다. 거리 측도는
  Euclidean / COSINE / DOT_PRODUCT. 별도 벡터DB(Pinecone/pgvector 등) 없이 현재
  스택 안에서 임베딩 저장 + 유사도 검색이 된다.
  - 출처: https://firebase.google.com/docs/firestore/vector-search ,
    https://docs.cloud.google.com/firestore/native/docs/vector-search
- 단 벡터 필드용 인덱스를 `gcloud` / Firestore 인덱스로 1회 구성해야 한다(공식 문서 명시).

### 3.2 임베딩 생성 -> 외부 모델 1개 추가 필요 (유일한 신규 의존성)

- 현재 의존성은 `@anthropic-ai/sdk ^0.98.0` 뿐이다. **Anthropic 에는 임베딩 엔드포인트가
  없다**(메시지 생성 전용). 공식 Firestore 문서도 "Firestore 는 임베딩을 생성하지 않으며,
  저장 전에 Vertex AI 같은 서비스로 벡터를 먼저 만들어야 한다"고 명시한다.
- 따라서 텍스트 -> 벡터 변환용 임베딩 모델이 새로 필요하다. 후보: Voyage AI(Anthropic
  공식 권장), OpenAI `text-embedding-3`, Google Vertex/Gemini embedding.
  - 비용·단가·차원수 등 제공자별 세부 사양은 **미확인**(도입 결정 시 별도 확인). 확정 사실은
    "Anthropic SDK 자체엔 임베딩이 없어 외부 모델 키 1개가 추가된다" 이다.
- 결과: Functions 에 임베딩 호출 코드 + 새 Secret(예: `EMBEDDING_API_KEY`) 1개가 늘어난다.

## 4. 우선 use case 분석: "답변 평가 근거 강화"

### 4.1 핵심 발견 - 설명본은 이미 평가에 주입되고 있다

`functions/src/answerEval.ts` 는 요청 body 의 `stepBody`(현재 단계 설명 본문)를 받아
`evalUserMessage(...)`(`functions/src/prompts.ts:314`)로 평가 프롬프트에 그대로 넣는다:

```
현재 단계: ${stepTitle} - ${stepDesc}
단계 본문 요약:
${stepBody}
평가할 질문/답변:
${qaText}
```

즉 "현재 단계의 설명본을 평가에 넣는다"는 RAG 의 가장 단순한 형태는 **이미 구현돼 있다.**
따라서 RAG 가 추가로 줄 수 있는 한계 가치(marginal value)는 "설명을 평가에 넣기" 가
아니라 아래 두 가지로 좁혀진다.

### 4.2 RAG 의 한계 가치(현 상태 대비 실제 이득)

1. **교차 세션 일관성**: 현재 `stepBody` 는 그 세션에서 갓 생성된 것이라 같은 개념도 세션마다
   설명이 흔들린다. 축적된 "검증된/대표 설명본"을 검색해 평가 기준으로 쓰면, 채점이 매번
   새로 생성된 본문이 아니라 안정적 기준에 묶인다(일관성 = 인터뷰가 꼽은 동기 중 하나).
2. **현재 단계 밖의 답변 채점**: 사용자가 현재 stepBody 범위를 벗어난 내용을 답할 때, 인접
   개념의 설명본을 검색해 주입하면 채점 근거가 넓어진다.

반대로, **현재 단계 답변을 현재 stepBody 로 채점하는 한** RAG 의 추가 이득은 작다.
이 점이 판단 기준 (a)(체감 품질)와 (c)(복잡도) 사이 트레이드오프의 핵심이다.

## 5. 도입 시 아키텍처 스케치 (Firestore 내장 기준)

> 도입을 결정했을 때의 형태일 뿐, 본 문서는 결정만 한다.

- **저장**: `stepDetail` 생성 시(또는 별도 배치) 설명본을 임베딩해
  `concepts/{conceptKey}` 같은 공용 컬렉션에 `{ embedding: VectorValue, body, concept,
  stepTitle, anonymized: true }` 로 적재. 익명화 = uid/세션 식별자 제거(인터뷰 합의: 교차
  재사용 허용).
- **검색**: `answerEval` 진입 시 `concept`(+질문 텍스트)를 임베딩 -> 공용 컬렉션에
  `findNearest` 로 top-k 설명본 검색 -> `evalUserMessage` 에 "참고 설명" 블록으로 주입.
- **신규 요소**: 임베딩 Function/헬퍼 1개, Secret 1개, 벡터 인덱스 1개, 공용 컬렉션 1개,
  Firestore 보안 규칙(공용 읽기/관리 쓰기) 갱신.
- 계약 영향: `answerEval` 의 입출력 시그니처는 유지 가능(서버 내부에서 검색·주입). 단
  품질 비교를 위해 "RAG 주입 on/off" 플래그가 있으면 A/B 가 쉬워진다.

## 6. 판단 기준별 평가

### (a) 체감 품질 개선
- 기대 이득: 교차 세션 일관성, 범위 밖 답변 채점 보강(4.2). 단 현재 단계 채점은 이미
  stepBody 로 커버되어 **체감 개선 폭은 use case 가 "일관성"에 가중될 때 큼**.
- 리스크: 잘못/저품질 설명본이 축적되면 RAG 가 오답 기준을 강화할 수 있다(garbage-in).
  익명 교차 재사용이라 품질 게이트(검증된 본문만 색인) 없이는 역효과 가능.

### (b) 비용 대비 효과
- 추가 비용: 임베딩 호출(저장 시 1회 + 평가 시 쿼리 1회), Firestore 벡터 저장/읽기,
  인덱스. 임베딩 단가는 일반적으로 생성 LLM 토큰보다 훨씬 저렴(추정, 제공자 단가 미확인).
- 절감: 첫 use case(평가 근거 강화)는 LLM 호출을 **줄이지 않는다**(평가 호출은 그대로,
  오히려 임베딩 호출이 더해짐). 비용 절감 동기는 이 use case 가 아니라 "콘텐츠 재사용으로
  생성 자체를 스킵"하는 후속 use case 에서 발생한다.
- 결론: 첫 슬라이스는 비용 기준으로는 **소폭 증가**. 비용 대비 효과는 품질·일관성 이득으로
  정당화해야 하며, 순수 비용 논리만으로는 첫 슬라이스가 약하다.

### (c) 구현·운영 복잡도
- 추가: Secret 1, 임베딩 헬퍼 1, 벡터 인덱스 1, 공용 컬렉션 + 보안 규칙, 품질 게이트.
- 운영: 임베딩 모델 벤더 1곳 추가(키 회전·장애 포인트), 색인 적재 파이프라인 유지.
- 현 스택이 Firestore 라 인프라 신규 벤더는 0(임베딩 제외). 복잡도는 "중" 수준.

## 7. 대안 비교 (RAG 가 과잉인지)

| 대안 | 일관성 | 범위 밖 채점 | 비용 | 복잡도 |
|---|---|---|---|---|
| 현 상태(stepBody 주입) | 낮음(세션마다 변동) | 약함 | 기준 | 낮음 |
| 프롬프트 보강(평가 루브릭 고정) | 중간 | 약함 | 기준 | 낮음 |
| 개념별 캐시(설명본 재사용, 벡터 없음 = 키 매칭) | 중상(같은 개념 키) | 없음 | 소폭↓ | 낮음 |
| RAG(벡터 검색 + 주입) | 상 | 보강 | 소폭↑ | 중 |

핵심: "같은 개념"의 일관성만 목표라면 **개념 키 기반 캐시**(임베딩 없이 정규화된 concept
키로 설명본 재사용)가 RAG 보다 싸고 단순하게 상당 부분을 달성한다. RAG 의 고유 가치는
"의미가 비슷하지만 키가 다른 개념"까지 묶어 검색하는 데 있다. 첫 슬라이스 목표가 동의어/
유사 개념 통합까지 포함하느냐가 RAG vs 캐시 선택을 가른다.

## 8. 권고

- **첫 슬라이스(평가 근거 강화) 단독으로는 RAG 도입 근거가 약하다.** 설명본이 이미 평가에
  주입되고(4.1), 비용은 소폭 증가하며(6b), 일관성 목표 대부분은 더 싼 개념 키 캐시로 가능
  하다(7).
- **RAG 의 진짜 ROI 는 "콘텐츠 재사용/추천"과 "유사 개념 통합"** 에서 나온다(생성 호출 자체를
  스킵 -> 비용 절감 + 중복 노드 완화, 연관 TODO 와 직결). 따라서 도입한다면 평가 근거 강화를
  단독 명분으로 삼기보다, 재사용/추천을 1차 가치로 두고 평가 근거 강화를 그 인프라의 부수
  활용으로 묶는 편이 정당화가 강하다.
- **제안 경로**: (1) 먼저 개념 키 기반 설명본 캐시로 일관성/비용을 싸게 검증 -> (2) "유사
  개념 통합·추천" 수요가 확인되면 같은 데이터에 임베딩을 얹어 RAG 로 승격. 벡터 인프라를
  처음부터 깔기보다, 캐시 -> RAG 점진 승격이 복잡도 기준(c)에서 유리하다.

(요지: 지금 첫 목표만 보면 RAG 는 비용만 늘고 이득이 작다. RAG 는 "재사용/추천"까지 갈 때
빛난다. 그러니 싼 캐시로 먼저 효과를 확인하고, 필요해지면 벡터를 얹어 키우자.)

## 9. 미해결 / 도입 결정 시 확인할 것

- 임베딩 제공자 선택 및 단가·차원·레이트리밋 (미확인).
- 색인 품질 게이트: 어떤 설명본을 "검증됨"으로 보고 색인할지 기준(garbage-in 방지).
- 익명화 범위 정의: 설명본에 사용자 입력 흔적이 섞일 수 있는지(개념 설명은 일반 지식이라
  위험 낮음으로 추정하나, stepDetail 생성 입력에 사용자 답변이 반영되는 경로가 있으면 확인).
- 첫 슬라이스 목표에 "유사 개념 통합"이 포함되는지 = RAG vs 캐시 선택의 분기점.
